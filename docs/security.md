# 当前安全与能力边界（V0、SSH、Tailnet 与直连网络）

V0 只在本机回环网运行，但每次操作仍经过证书和当前配对信任。数据目录内私钥、证书、owner token、数据库、配置和每次运行数据各自独立。Windows 使用仅当前用户可访问的 ACL，Unix 使用 0700/0600；init 拒绝覆盖未完成身份或非空的无关目录。相同 data-dir 的第二个 Daemon 因目录锁失败。

显式 Tailnet 模式每次启动须通过本机 Tailscale CLI 验证运行/在线及确切监听 IP；只绑定该字面 IP，并给新证书加入对应 SAN。公开监听仅接受 Tailnet 地址来源，拒绝整个 `/local/*`，即使请求携带 owner 证书和 token；owner 经独立回环 socket 管理。候选发现只显示必要网络元数据，不自动信任、授权或调用模型。默认回环实例不能主动连接别的电脑，owner 客户端不向任何网络发送 token。名片和配对码只用字面 IP；只有已配对电脑之间交换的地址列表、以及 owner 手动填的地址可以写主机名（见下面的「地址列表」）。详见 [直连说明](quickstart-tailnet.md)。

**直连网络（`network = "direct"`）。** 不用 Tailscale：电脑之间走它们本来就连得通的网络（局域网、ZeroTier、WireGuard 等）。以前配置明确禁止监听局域网和公网地址，直连模式有意放开了这一条，换成下面几道关：

- **监听所有网卡，只对认过的网络开门**：`hmesh setup --full --network direct` 新装的电脑配置成 `listen_address = "::"` 加 `trusted_networks`：一个双栈端口（IPv6 不可用时退回 `0.0.0.0`）开在所有网卡上。以前只许监听一个字面地址，是因为通配监听会把端口开到电脑所在的每个网络上，包括咖啡馆的 Wi-Fi；现在端口虽然在每张网卡上都开着，每条连接在 TLS 握手之前都先过一道「围栏」，按两个地址决定去向：本机这一端的地址是回环、来源也是回环的，走 owner 路由（规则和原来独立的回环监听一样：要 owner 证书和 token）；其余的，本机这一端的地址必须在某个认过的网络上（或者是 Tailscale 条目对应的本机 Tailscale 地址），来源必须在 `allowed_sources` 里（Tailscale 地址只接受 Tailnet 来源，而且这个来源不能在本机所在的某个局域网的网段里），否则直接断开：对方连 TLS 握手都做不了，看不到证书，也碰不到配对接口。从别的电脑进来的连接只走对端路由，拒绝整个 `/local/*`。`trusted_networks = []` 表示谁也连不进来，只能往外连。`0.0.0.0` 和 `::` 只在这种配置下允许（`0.0.0.0` 只监听 IPv4）；多播、广播地址一律不允许。
- **怎么认网络**：一条记录是「子网 + 网关的硬件地址」：家里和咖啡馆可能都是 192.168.1.0/24，但网关不是同一台设备。daemon 每 5 秒看一次本机网卡和子网（`if_addrs`，不看回环、链路本地这些 `peer_address` 不允许的地址）、默认网关（macOS `/usr/sbin/netstat -rn -f inet`，Linux `/proc/net/route`，Windows `C:\Windows\System32\ROUTE.EXE print -4`）和网关的硬件地址（`/usr/sbin/arp -n <网关>`、`/proc/net/arp`、`C:\Windows\System32\ARP.EXE -a <网关>`）：命令用绝对路径，2 秒超时，读不到就当没有。信任时读不到网关的硬件地址（没有默认路由，或者 ARP 表里没有它），这条记录就只按网段认（`subnet_only`）：同网段的别的网络也会被当成认过。`hmesh networks trust` 和 `list` 的输出（`subnet_only` 和 `notes` 里的一句话）、面板「这台电脑」卡片、setup 的步骤说明都会标出「只按网段」；到能看到网关的时候再信任一次，就绑定到那个网关。记了网关、但此刻 ARP 表里没有它的网络，暂时只按网段认，标成 `gateway_unverified`，同样有说明。硬件地址能被同一网段里的人伪造，它防的是「到了另一个同网段的网络」，挡不住站在同一个网络里、有备而来的人；挡那种人靠的是固定的证书指纹和配对窗口。只能信任此刻所在的子网（`hmesh networks trust <子网>`、面板「这台电脑」卡片上的「信任这个网络」、`POST /local/networks/trust`），网关硬件地址由 daemon 从它自己的观察里填，调用方填不了；写回 `node.toml`，同时换掉内存里的围栏，不用重启。`hmesh networks forget <子网>` 立刻关上：新连接在 TLS 之前断开；从那个网络进来、已经开着的连接（长请求、别的客户端保持的连接）每秒复查一次围栏，不再放行时按关机那样优雅关闭：不再接新请求，正在处理的请求最多再等 3 秒，所以最晚 4 秒左右断开；离开了某个认过的网络也一样。审计 `network.trust`、`network.forget`（只记子网，不记硬件地址）；`hmesh doctor` 的输出是拿去求助用的，网关硬件地址和口令一样写成 `hidden`。Tailscale 条目（`tailnet = true`）表示本机的 Tailscale 地址也接受连接，来源必须是 Tailnet 地址。Tailscale 用的 100.64.0.0/10 也是运营商级 NAT 的网段，酒店、校园网、运营商的 Wi-Fi 也会发这种地址，所以地址范围本身不算数：本机地址里有这个范围的地址时，问 Tailscale CLI（`status --json --peers=false`：只问本机，不列整个 tailnet，免得大 tailnet 的输出超过上限或超时；2 秒超时，答案在地址不变时缓存 30 秒）哪些是它自己的：BackendState 是 `Running`（在运行、已登录）就用它报的本机地址，暂时连不上协调服务器（`Self.Online` 为 false）时也一样，因为和已经连上的电脑之间照样能通；停了、没登录、还在启动就一个都不是；问不了（没装、没答复）时，只认 Tailscale 自己命名的网卡（Linux 的 `tailscale0`、Windows 的 `Tailscale`），macOS 的 `utunN` 谁都可能用，不算；拿不准就不算 Tailscale。CGNAT 的 Wi-Fi 因此只是一个普通网络，不认它就连不进来；就算认了 Tailscale，来源落在本机局域网网段里的 Tailnet 范围地址（隔壁的 100.80.7.7）也不能经 Tailscale 地址进来。
- **地址变了不用重跑 setup**：认过的网络上的本机地址一变，围栏、名片地址和地址列表跟着更新（地址列表的 revision 设成当前毫秒），并立刻推给已配对的电脑，不等 5 分钟。名片取第一个认过的局域网地址，没有就取 Tailscale 地址，都没有就保持上一个。调试构建里，环境变量 `HMESH_TEST_NETWORKS` 可以让 daemon 从一个 JSON 文件读网络（集成测试用它模拟换网络，每次都重读）；发布构建里没有这条代码。
- **单地址配置（以前的）**：`listen_address` 是本机一个字面地址的旧配置照常工作：只绑定那个地址，owner 走独立的回环监听；启动时绑不上（例如 DHCP 换了地址）就退出，并提示重跑 `hmesh setup`。重跑 setup 会把它迁移成监听所有网卡，信任那个地址所在的网络（地址已经不在了就按新装的规则：交互时问，没人可问时什么都不认）。setup 没人可问时（没有终端、`--json`）不替你认任何网络，也不开 Tailscale：只认 `--listen`、`--trust` 写明的，Tailscale 要 `--with-tailscale`。回环地址代表不了一个网络（它分不开 owner 和别的电脑），所以 `--listen 127.0.0.1` 这种测试和演示用的配置保持单地址。
- **来源网段**：对外监听只接受 `allowed_sources` 里的来源，不在网段里的连接在 TLS 握手之前就丢掉（监听所有网卡时，这一条和「认过的网络」在同一道围栏里一起检查）。不配置时默认是私有网段：10/8、172.16/12、192.168/16、100.64/10、fc00::/7，以及回环地址。监听公网地址时必须显式配置，否则配置校验不通过。网段只是第一道篱笆，不是认证。
- **配对窗口**：hello、challenge 和配对申请这几个匿名接口，只在 owner 打开面板的「配对新电脑」或运行 `hmesh pair show` 之后的 10 分钟内回应，其余时间回 `PERMISSION_DENIED`。这样平时别人连配对申请都发不进来，批准列表里只会有窗口那 10 分钟里收到的申请。窗口不隐藏证书：TLS 握手照常把证书出示给允许网段里的任何连接，所以指纹不是秘密；防冒充靠的是批准时核对校验码，以及「多条申请对得上同一个校验码就拒绝批准」。对已有申请的状态查询不受窗口限制：申请 ID 是随机的，只有发申请的一方知道。已配对的电脑互相探测在线和读取 agent 走带证书的接口，也不受窗口限制。配对窗口只记在内存里，daemon 重启后就关上。
- **按来源限流**：所有网络上的匿名接口都按「来源 IP 每分钟」计数，同时不能超过「所有来源合计的 10 倍」。超出本来源额度而被拒的请求不计入合计，所以一个地址不停地发，也占不掉别人的额度。按地址计数：一台机器用上很多地址（比如 IPv6 下同一网段的多个地址）仍能多占几份，最多到合计上限；来源网段越窄，能用的地址越少。
- **能连的地址**：对端地址可以是任何字面单播 IP，包括局域网和公网地址；只拒绝链路本地地址（169.254.0.0/16 是云主机元数据服务所在的网段，fe80::/10 需要区域标识）、未指定地址、多播、广播和保留地址。名片和配对码不接受域名；地址列表和手动地址里可以写主机名，拨号时用系统解析，解析出的每个 IP 照样过这条规则，不过的丢掉。对端到底是谁，由固定的证书指纹决定，和地址无关。
- **局域网发现**：直连模式下，接受连入的电脑只在配对窗口开着、口令还没用掉时，用 mDNS 广播 `_hmesh._tcp`：内容只有电脑名、监听地址、端口和发现协议版本，不带证书指纹；只在监听地址所在的那张网卡上广播（监听所有网卡时，只在认过的局域网地址上广播，没认过的网络上不广播），主机名每次随机。窗口一关、口令一用掉就撤回（发 goodbye 包）。别的直连电脑（包括只装 MCP 的）在配对弹窗里列出听到的电脑，并且只列出此刻还能连上那个地址的（非正常退出、没来得及撤回广播的电脑会被滤掉）。听到的名字证明不了任何事：同一网络里谁都能广播一个同名服务，确认身份靠下面的口令。
- **已配对的电脑互相找回**：每台电脑有一把随机的找回密钥（32 字节，存在本机数据库的 `node_secrets` 表里），只随地址列表经要证书的接口交给已配对的电脑（字段 `find_key`，对方存进 `peer_addresses.find_key`）；它不进日志、事件、审计和 `hmesh doctor` 的输出。接受连入的直连电脑只要有认过的局域网地址（单地址配置就是它监听的那个地址），就一直用 mDNS 广播 `_hmesh-find._tcp`：实例名是「找回密钥对当前 10 分钟（unix 秒除以 600，8 字节大端）算的 HMAC-SHA256」的前 16 个十六进制字符，每 10 分钟换一个（先撤回旧的再广播新的）；主机名每次随机，TXT 只有 `v=1`，地址只有认过的局域网地址，端口是监听端口；不带电脑名，也不带指纹。只往外连的电脑、没认过的网络和 Tailscale 地址上都不广播。外人能看到的是：这个地址和端口上有一台电脑提供这个服务（端口本来就扫得到），名字是一串每 10 分钟换一次的随机字符，名字里没有电脑名和指纹。但它藏不住是哪台机器：配对窗口开着时，同一台电脑还在广播带电脑名的 `_hmesh._tcp`，两条广播是同一个 IP 和同一个端口，同一网络里的人一对就知道这个标记是哪台电脑的；窗口关了以后换的只是标记，地址和端口不变，见过它的人照样按地址认得出。标记管的是另外两件事：没有找回密钥的人算不出下一个标记（被撤销的电脑也算不出，见下文）；有人照抄标记在别的地址上广播，已配对的电脑连过去也过不了固定证书这一关。直连网络的电脑调用已配对的电脑时，所有已知地址都在请求发出去之前失败、并且对方给过找回密钥，就在局域网里听 1.5 秒，只在它自己会广播标记的网卡上问和听：单地址配置是监听地址所在的网卡，监听所有网卡时是认过的局域网地址所在的网卡（一个局域网都没认过就不找）；只往外连的电脑没有认过的网络，就在默认路由所在的那张网卡上问和听（它本来就从这张网卡往外连；不在它上面听，就找不回换了地址的电脑）。别的网卡（VPN、虚拟机网桥）和 Tailscale 都不问。找回用一个单独的 mDNS 实例，启动后先关掉所有网卡、只打开这几张，再发查询；「附近的电脑」照旧在所有网卡上听。听到的：名字等于对方这 10 分钟或上 10 分钟标记的，把它广播的地址加进候选再试一轮，连上的那条记进对方的地址列表（排在最前面，等对方给出更新的列表时被替换）并设成 `last_good`。同一台对端 30 秒内最多找一次，这期间用上一次听到的结果；查找在后台跑完，调用方先不等了也不白找。听到名字不等于信任：连上以后仍然要出示配对时固定的那张证书，对不上就跳过。撤销任何一台电脑时，先把它标成已撤销，再换一把新的找回密钥，地址列表的 revision 跟着变，新的列表马上推给其余连得上的已配对电脑。被撤销的那台拿不到新钥匙：后台推送的每一轮都先取地址列表、再取要推给谁，推的是这一轮开始时的那一版，每推一台之前再查一次它是否仍是已配对的，这一轮里撤销的就不再推给它；对方来拉列表时也是先取列表、再核对它的证书。只往外连的电脑下次来拉时才拿到（每 5 分钟一次），这期间本机要是换了地址，它也认不出新标记。被撤销的那台只有旧钥匙，算不出新标记；就算它靠扫端口找到了地址，本机也不再接受它的证书。
- **6 位口令配对**：打开配对窗口时生成一次性 6 位口令（每个数字等概率），只显示在本机面板和 `hmesh pair show` 里。对方选中这台电脑、输入口令后，两边做 SPAKE2（RustCrypto `spake2` 0.4，Ed25519 群）：口令本身不上网络，双方的证书指纹是 SPAKE2 的身份参数，再用协商出的密钥各发一个 HMAC-SHA256 确认（绑定配对申请 ID）。所以口令不对、或者中间有人冒名转发（他出示的是自己的证书），确认都对不上，谁也不会被信任；冒充的一方每握手一次只能猜一个口令，拿不到能离线试的东西。每个口令只能试 3 次：每开始一次握手就用掉一次；问方发现对不上时会发一个空确认告诉答方。错满 3 次口令就作废、停止广播（问方不发确认也一样：次数用完、又没有进行中的握手，口令就作废），但配对窗口照开：粘贴配对码的路不受影响，所以猜口令的人堵不住配对；要再用口令就换一个新的。冒充的一方猜中的概率是百万分之三。对上之后，答方先消费 challenge、记下申请并信任问方（不再要人批准），成功了才作废口令；问方在发确认之前先记下自己的申请，确认的回应丢了也会在后台照常完成，对方明确拒绝时就把申请关掉。问方随后照常确认答方已经接受了自己的证书，再信任答方。配对申请签名（证明持有私钥）、challenge 一次性、来源限流、配对窗口这些照旧。口令和协商出的密钥不进日志、事件和审计；审计只记 `pair.passcode` 和对方节点 ID。口令只给 owner 看（面板、`hmesh pair show`、`hmesh daemon status`）；常被贴出去求助的 `hmesh doctor` 把它显示成 `hidden`；`hmesh pair join` 不带 `--passcode` 时提示输入，口令就不会留在 shell 历史里。
- **按地址配对**：问方也可以不从「附近的电脑」里选，直接填答方的 IP 或主机名（面板配对弹窗的「按地址配对」、`hmesh pair join <地址>`），不带端口就用 `hmesh setup` 的默认端口 39880。主机名照地址列表的规则解析（只用 `peer_address` 允许的 IP），确认身份照样只靠口令。配对完成后，和名片地址不同的那个地址记成这台电脑的手动地址。
- **第一次连接**：问方还不知道答方的指纹，所以第一个 hello 请求接受对方出示的任何证书（仍检查编码和有效期），记下它的指纹，并要求和 hello 名片里的指纹一致；之后的请求都固定这个指纹。这一步不建立信任，信任只来自口令确认。
- **两端都要升级**：旧版本只接受 Tailnet 地址的对端，还会核对证书里是否写着拨号用的 IP，所以用直连的两台电脑都要装这一版或更新的版本。只用 Tailscale 的电脑之间不受影响。
- **macOS 本地网络权限**：macOS 要求进程有「本地网络」权限，才能向局域网地址发起 TCP 连接（[Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)）。从终端运行的命令和 launchd daemon 自动放行，开机自启装的 launchd agent 不在放行之列。被拒绝时连接会报 `EHOSTUNREACH`，HarnessMesh 会把它翻译成去「系统设置 → 隐私与安全性 → 本地网络」打开权限的提示。Tailscale 等 VPN 地址不算本地网络，不受这条影响。局域网发现收发多播，同样需要这个权限。macOS 版 `hmesh` 内嵌 Info.plist（`NSLocalNetworkUsageDescription` 说明用途，`NSBonjourServices` 声明 `_hmesh._tcp` 和 `_hmesh-find._tcp`），打包时重新做 ad-hoc 签名把它绑进签名，标识为 `dev.harnessmesh.hmesh`，这样系统能弹出授权并记住同一个程序。

**只装 MCP（只出不进）。** `hmesh setup --mcp-only` 建的节点在本机装了并登录了 Tailscale 时是 `network = "tailscale"`，否则是 `network = "direct"`，两种都是 `expose_to_tailnet = false`：只在回环地址上开一个监听，不对外监听，也不在启动时要求 Tailscale 在线；Tailscale 节点配置里的 `tailnet_address` 只写进证书 SAN，留给以后换成完整安装时用。Daemon 对任何不是本机 owner 的请求一律回 `PERMISSION_DENIED`：已配对节点的受认证请求、匿名的 hello、challenge、配对申请和申请状态查询都一样，所以它只能主动向外配对和调用，别的电脑什么都调用不了它，也看不到它的 agent。完整安装的节点看到对端名片的地址是回环地址时，就把它当成只出不进的电脑：不探测、不调用，面板上显示「只调用」。

**名片更新。** 已配对且受信任的节点可以 `POST /hmesh/v1/peers/card` 更新自己在对方那里的名片：要求名片的 node_id 等于连接认证出的节点、指纹等于这条连接的证书指纹，并通过和配对时相同的 `validate_card` 校验；不会改动信任状态，也不会接受别的节点的名片；每次更新记一条 `peer.card` 审计。每个 Daemon 启动时把自己的名片发给每个受信任的对端，没送达的每 5 分钟重试。只出不进的节点拒绝这个接口，收不到对方的新名片；它靠下面的地址列表找到换了地址的电脑。

**地址列表。** 名片仍然只有一个地址：旧版本严格校验名片，多一个字段就整张拒收。其余地址放在只给已配对电脑的接口里。`GET /hmesh/v1/peers/addresses` 返回本机的地址列表：名片地址，监听所有网卡时再加上本机在认过的网络上的其余地址（包括 Tailscale 地址），再加上 `node.host_names` 里每个主机名的 `https://<名字>:<端口>`；没配置 `host_names` 时，接受连入的电脑默认用系统主机名（小写，不合法的字符换成 `-`，补上 `.local`），只往外连的电脑列表为空。`POST /hmesh/v1/peers/addresses` 让对方推送它自己的列表：要求发送方是受信任的对端、列表的 `node_id` 是它自己；最多 16 条，每条不超过 300 字节，每条都要过 `validate_peer_address`（规则同名片地址，另外接受 DNS 主机名：每段只有小写字母、数字和 `-`，不以 `-` 开头结尾，总长不超过 253）；只有 revision 更新时才替换；审计 `peer.addresses` 只记条数。接受连入的直连电脑的列表里还带它的找回密钥 `find_key`（64 个小写十六进制字符，格式不对整条拒收；见上面的「已配对的电脑互相找回」），和列表一起存、一起替换。两个接口都要客户端证书，地址列表和找回密钥不会出现在配对码、mDNS 广播或匿名接口里。每个 Daemon 启动时、配对完成时、本机在认过的网络上的地址变了时，以及此后每 5 分钟，向每台能叫到的受信任电脑拉一次对方的列表；自己的列表每个 revision 只推一次：对方收下了，或者回了错误（比如没有这个接口的旧版本），就不再推，没送达的（对方没开机、连不上）下一轮再推。地址变了 revision 跟着变，新的列表马上推（名片换了地址也再推一次名片）。只装 MCP 的电脑不接受连入，就是靠拉来知道对方的新地址。旧版本没有这两个接口，推过去回错误也算推过，不再重试，名片照常同步。owner 还可以给对端手动加地址（`hmesh peers address`、面板电脑卡片上的「改地址」、`POST /local/peers/{id}/addresses`），只存在本机，审计 `peer.addresses.manual` 只记条数。撤销配对不删这些记录（重新配对时还能用），但只有受信任的对端才会用到它们。

**多地址拨号。** 调用已配对的电脑时，按「上次连上的那条、名片地址、手动地址、对方给的地址」去重后依次试，只用本机能叫的地址（`can_call`）。只有一条地址时给它 3 秒建连接（解析主机名、TCP 和 TLS）。有多条时，排在最前面的那条也给满 3 秒，所以慢但通的路（比如经 DERP 中转、每个来回几百毫秒的 Tailscale）照样用得上；它 200 毫秒内还没连上，就同时和其余每条地址做一次 TLS 握手探测（不发请求，证书不是配对时固定的那张就算失败）。有一条握手成功、而第一条这时还没连上，就放弃第一条，改用那条发请求；第一条已经连上了，就不再探测别的地址，等它的回答，回答再慢也等。「连上」和「放弃」由每次尝试自己的一个原子状态裁决，先到的算数：放弃之后才建好的连接直接丢掉，一个字节的请求都不发；已经连上的尝试不会被放弃。第一条真的连不上（被拒、证书不对、3 秒内没建好连接），就按握手成功的先后试别的地址，已经握手成功的马上用，探测不通的不再试；主机名地址直接用探测时连上的那个 IP，不再解析一次，第一条 200 毫秒内连上时也根本不去解析别的主机名。所以一条不回包的地址（比如电脑离开了的那个网络上的地址）只多花 200 毫秒加一次握手，调用方最短的 750 毫秒等待够用。只在请求还没发出去时换下一条：TCP 连不上，TLS 握手失败（包括对方出示的证书不是配对时固定的那张），建连接超时，或者连接还没建好就被放弃；请求发出去以后的超时、HTTP 错误和业务错误照常返回，所以一个写请求不会在两个地址上各执行一次。主机名用系统解析（`.local` 走系统的 mDNS：macOS 自带，Linux 要装 Avahi 和 nss-mdns，Windows 还没测过），只保留 `peer_address` 允许的 IP。证书固定不变，所以解析错了、或者那个地址上是另一台电脑，最多是连不上：它拿不出那张证书的私钥。代价是一台受信任的电脑能让本机去连它列出的地址（最多 16 个，只做 TCP 连接和 TLS 握手，证书对不上就不发请求，也从不带 owner token），这和它本来就能在名片里写任意单播地址是一回事；链路本地地址（含 169.254.169.254）永远不连。连上的地址记成 `last_good`（内存里，变化时写进数据库，下次启动先试它）；`/local/peers` 的每台对端带 `routes`（`advertised`、`manual`、`last_good`、`last_good_at`）。全部失败时（直连网络的电脑先按找回密钥在局域网里找一次，见上面）返回 `PEER_UNREACHABLE`，逐条说明每个地址卡在哪一层，用的是固定的英文短语：`refused the connection`（连接被拒）、`did not answer`（超时）、`did not resolve`（解析不出来）、`is another computer`（证书不对）、`has no route from here`（没有路由）、`could not be reached`、`failed the TLS handshake`，在局域网里也没听到它时再加一句 `it was not heard on the local network either`。面板不拿到错误原文，只拿到从这些短语读出来的固定原因（`reasons`：`refused`、`silent`、`unresolved`、`another_computer`、`no_route`、`unreached`、`tls`、`not_heard`），再用中文说一句；`/local/peers` 的每台对端在连不上时也带同样的 `unreachable_reasons`（调用方先不等了的那次，用一分钟内最后一次失败的原因），它回 hello 却不接受本机证书时是 `not_accepted`（多半是它那边撤销了配对）。回环模式的节点只拨回环地址；owner 凭据仍然只发往本机。

## 认证和授权

TLS 只允许 1.3。客户端先核对明确的 SHA-256 证书 pin，再由 rustls/WebPKI 验证证书编码、有效期、用途与握手签名，不存在接受所有证书的模式。证书不再需要写着拨号用的那个地址：指纹已经锁定了唯一一张证书，TLS 握手又证明对方持有它的私钥，再核对地址不增加保护。这样局域网地址变了、换了网卡或网络，都不用重新配对。所有 HarnessMesh 证书都写有 localhost，WebPKI 统一按这个名字检查。匿名入口仅用于 hello、单次 challenge、签名配对申请和申请状态查询；challenge 有目标绑定、过期和使用一次的约束。

配对只需对方 owner 批准一次：发起方核对对方的 pin（配对码里带着完整指纹）发出申请，此时双方都不信任对方。对方 owner 核对发起方的校验码（发起方证书指纹的最后 6 位）后批准，对方开始信任发起方。发起方的 Daemon 每 3 秒查一次申请状态；查到「已批准」后，再用自己的证书连一次对方的受认证接口，对方接受了这张证书才在本机信任对方，所以发起方不会在对方批准前、也不会只凭一个状态词就开放自己的 agent。状态查询是匿名的（发起方这时还不被信任），只回 pending/approved/declined/revoked/expired 一个词，只有持有随机申请 ID 的一方能查，并和其他握手请求共用每分钟 60 次的限额。过了有效期，发起方仍先问对方再下结论（对方可能在发起方关机或休眠时批准了），之后每分钟问一次，问到确定答案为止，连续一天联系不上才记为过期。对方拒绝或申请过期，发起方的申请随之结束；发起方取消自己的申请，或撤销对方的配对，都会结束和对方之间所有等待中的申请，之后对方再批准也不会让发起方重新信任它。

批准时校验码不对，面板拒绝批准。6 位校验码只有 24 位：在 Tailnet 里的人可以专门生成证书，离线试上千万次碰出同样的 6 位，冒充一条申请。所以面板在多条等待中的申请对得上同一个校验码时拒绝批准，并显示对方的地址；需要更强的保证时，用 CLI 的 `pair approve --expect-fingerprint` 核对完整指纹。

**配对是信任边界。** 已配对且仍受信任的节点可以看到本机登记的 agent，并能和它们开会话或派活；未配对或已撤销的节点什么都看不到、什么都派不了。每个对端有一个访问模式（policy 的 `[peers]` 段，默认 `auto`）：`auto` 直接开始，`confirm` 让会话停在 `pending_approval`、任务停在 PENDING_APPROVAL，等本机 owner 批准（`hmesh peers access`）。会话只允许打开它的那台电脑（和本机 owner）读取、追问、取消和关闭；权限请求由打开者回答，agent 打开的会话在 `auto` 下自动允许一次、在 `confirm` 下由本机 owner 回答。撤销配对会关闭对方在本机打开的会话。发送方也可以主动要求审批（开发流程的阶段任务就是这样）。旧的 `[[grant]]` 项目授权和 agent 的 `require_remote_task_approval` 仍可解析，但不再参与决定。agent 只在它登记的项目目录里工作。登记 Agent 只能由本机 owner 完成。只通过版本探测的 Agent 保持 unverified，真实 owner 验证成功后才能接收 peer 任务。任务在出队前和启动前重新检查配对信任。撤销也在每次 HTTP 请求中重查，因此连接复用不会保留旧授权。

owner API 必须同时具备自己的客户端证书、该实例的私有 token 和回环来源；信任的 peer 无法操作它。任务读、事件、核验结果和取消仅对原发起 Node 或执行端 owner 开放。审计记录授权决定、task/attempt/trace，以及审批、拒绝、取消、策略更新和信任撤销；不会把模型账户密钥当作审计字段。

## 受管开发服务与 SSH

服务发布、隧道配置、连接建立及联调启动只在本机 owner API 开放。服务 peer 白名单和可选 restart 白名单由 owner 明确设置；task grant 不会自动授予服务访问。远端服务卡隐藏内部端口、命令和环境。restart 仅使用原 owner 配置；MCP 会话工具没有这些管理能力。

HTTP 桥接每次重查当前信任和服务租约，缓冲响应释放前再次重查。两侧正文各不超过 256 KiB，最多八个本地并发请求，不转发 Cookie/Authorization，不自动重定向或重放写请求。SSH 使用独立空配置、显式身份及 known_hosts、strict host key 和最多两个固定回环端口转发；不能指定任意目标地址或 SOCKS。原用户 SSH 配置及已有转发不变。

进程由 owner 绝对路径和项目 root 启动，不接管占用端口或历史 PID。初启加最多三次自动重启，租约至多一小时；Daemon 正常停止回收自己的进程树。重启不复活旧授权，Unix 非正常强杀后可能有孤儿进程，owner 必须独立核查，不能依靠历史 PID 杀进程。OS 常驻安装及崩溃接管未实现。

联调固定保存契约/测试计划及其 hash，最多两次修复；确定性程序验收，模型完成不代表测试通过。原任务审批继续生效，远端审批不能由模型代行。网络或任务结果未知时停止，不生成新 UUID 猜测执行。报告记录响应 hash/断言，不包含响应正文；配置/契约与预期断言也应避免敏感信息。服务 env 属于本机 owner 私有配置，当前没有服务凭据管理器。细节见 [受管服务说明](managed-services.md)。

## Agent 运行机制（ACP）

HarnessMesh 只通过 [Agent Client Protocol](https://agentclientprotocol.com) 驱动 agent：以参数数组直接启动 owner 登记的 ACP 命令（`opencode acp`、`claude-agent-acp`、`codex-acp`、`pi-acp`、`dsh --profile acp` 或其他），工作目录默认是登记的项目目录，不拼 shell 命令。远端不能改变命令、环境或参数，也不能传入路径（见下面「项目」）。默认 agent 用它自己的登录和模型设置；HarnessMesh 不读取、不复制、不导入任何 agent 的凭据文件（旧的 `credential_source` / `models_file` 已移除并会被拒绝），只有 owner 在「模型服务」里给的值会以环境变量交给 agent（见下）。owner 在 `env_allowlist` 里列出的环境变量缺失时，启动前失败。

客户端在 `initialize` 里声明不提供文件系统和终端能力，agent 用自己的工具读写项目。agent 的每个 `session/request_permission` 都由会话的回答方决定（见上节）；一次性任务只允许 owner 在 `allowed_tools` 里列出的工具类别，其余一律拒绝并以 `FAILED_NEEDS_INPUT` 结束。**固定工作目录和权限回答不构成 OS 文件系统沙箱**；agent 进程拥有当前用户的底层权限，只应登记可信项目。

### 项目和 agent 已有的会话

- **项目**是本机的文件夹：每个登记 agent 的目录自动是一个项目，owner 可以通过 `/local/projects` 添加更多（必须是已存在的绝对路径，按解析符号链接后的真实路径存，同一文件夹只存一次）。本机 owner 和本机发起的调用链可以让任意本机 agent 在任意项目里开会话（`OpenSession.project_id`），agent 进程的工作目录和 ACP `cwd` 都换成该项目。
- **共享项目**：项目默认不共享。owner 打开共享后，配对电脑经 `GET /hmesh/v1/projects` 只拿到项目 ID 和名字，**拿不到路径**；隐藏的项目即使仍在共享也不再列出；已知道项目 ID 的对方仍能用它，要停用就取消共享。它开会话时只能带项目 ID（`PeerOpenSession.project_id`），本机用自己的项目表换成路径并检查仍在共享，不在共享就拒绝。agent 自己的登记目录不需要共享。配对电脑发起的调用链在本机开子会话时同样只能用共享项目，它的 MCP 服务器在 `mesh_list_agents` 里也只列出本机的共享项目，未共享项目的名字不会经 agent 的回复传回对方。会话记录里的本机路径（`cwd`）在发给配对电脑前去掉，所有返回会话记录的 peer 接口（开会话、查询、事件、发消息、命令、权限、取消、关闭、设置）都一样。取消共享后，对方在这个项目里已开的会话从下一轮起被拒，查看命令、改设置等任何会启动 agent 的操作也被拒（每次启动 agent 前都检查）。共享后对方的 agent 能按工具白名单读写该文件夹，固定工作目录**不构成文件系统沙箱**。
- **agent 已有的会话**：只有本机 owner 能调 `/local/projects/{id}/history` 和 `/local/history`。daemon 临时启动 agent，只发 `initialize` 和 ACP `session/list`（最多 20 页、1000 条、45 秒），然后停掉；不建会话、不调模型，HarnessMesh 不读取、不复制、不改写 agent 自己的会话文件，标题经脱敏后只在本机显示。接上旧会话（`OpenSession.resume`）只限本机 owner 本人（agent 发起的调用和配对电脑都会被拒），由 agent 自己 `session/load` 回放；回放的历史在第一次接上成功后一次性保存为会话事件（每条标 `replayed`）；接上失败或中途停止时一条都不存，下次接上再完整存一次，存过之后不再存。触发成功接上的那条消息记在历史之后；之前接上失败时发的消息已经先记下，会排在历史前面。历史还没接上时发的消息先以排队事件存进库，agent 启动后、会话被关闭时或 HarnessMesh 重启后转成正式消息，不会丢也不会重复。回放结束由处理事件的一方按顺序判定，回放 120 秒内没处理完就放弃这次启动、什么都不存，下次发消息时重来。没有对应的 peer 接口，旧会话不会发给配对的电脑。
- **会话标记**（改名、置顶、隐藏）只存在本机 `session_marks` 表里，不发给 agent，也不发给配对电脑。

每个打开的会话对应一个长驻 agent 进程，空闲 10 分钟后停止。下次发消息时，HarnessMesh 根据新进程的 ACP 握手续上原会话。声明 `loadSession` 的 agent 使用 `session/load`，DSH 使用 `session/resume` 恢复上下文，面板从本地记录显示历史。恢复请求失败时，本轮停止并保留原会话 ID，便于重试。两种恢复能力都未声明的 agent 会开新会话，并提示之前的上下文已丢失。登记 agent 只做一次 `initialize` 握手，不创建会话、不调用模型。

### 会话设置和模型服务

- **会话设置**（模型、模式、思考强度）走 ACP 的 `session/set_config_option`，打开会话的电脑可以在两轮之间修改，值由 agent 校验。用户的选择记在会话上，进程恢复后，HarnessMesh 会把已经回到默认值的选项重新设为用户所选的值。
- **模型服务**（每个 agent：用它自己的登录 / API key / 自定义地址、默认模型、额外环境变量）只能由本机 owner 通过 `/local/agents/{id}/service` 设置，存在 `<数据目录>/agent-secrets/<agent id>.json`（目录 0700、文件 0600，原子写入），和节点私钥同一级保护；没有对应的 peer 接口，配对电脑只看到 `service_configured` 和默认模型名，看不到 key。接口只写不读：返回值只说「已设置」和长度足够时的末 4 位。
- 启动 agent 进程时按类型换成环境变量：OpenCode 用 `OPENCODE_CONFIG_CONTENT` 注入一个 `hmesh` 服务商（地址是本机转发，见下一条；转发的令牌放在单独的 `HMESH_OPENCODE_API_KEY` 里，配置文本里只有 `{env:…}` 引用；模型列表里的模型都注册进去，并用 `enabled_providers` 让会话只在这些模型之间切换，不会切到用户自己 OpenCode 账号下的模型；标题等小请求也走同一个地址），Claude Code 用 `ANTHROPIC_API_KEY` 或 `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`，Codex 用 `OPENAI_API_KEY` / `OPENAI_BASE_URL`，Pi 与 DSH 使用按 Agent 生成的服务商配置和专属环境变量。通用 ACP 可指定它读取 Key 的环境变量名。冲突的继承变量会被去掉。**不改用户自己的 agent 配置文件**。
- **OpenCode 自定义地址走本机转发**：有的 OpenAI 兼容网关（如 `api-gateway.glm.ai`）流式回复的最后一块带 `delta.role: ""`，OpenCode 内置的 AI SDK 只认 `"assistant"` 或不带，收完回复后整轮报 `Type validation failed`。所以 daemon 在 `127.0.0.1` 的随机端口上开一个转发（第一个用到它的 agent 启动时才开），OpenCode 连 `http://127.0.0.1:<端口>/relay`，拿到的是一个随机令牌（`hmr-` 开头，同一地址、协议和 Key 复用同一个，daemon 重启后作废），**真 key 只在 daemon 里**，OpenCode 进程的环境变量里没有。转发只接受已知令牌，路径只能接在配好的地址后面（换不了主机），不跟随重定向，去掉 `Authorization`、`Cookie`、`Accept-Encoding` 等本跳的头再带上真 key；回复原样流回，只把 `choices[].delta` / `choices[].message` 里值为空字符串的 `role` 删掉（流式逐行处理，单行超过 4 MiB 或压缩过的回复原样放过）。不记录请求和回复内容。OpenCode 的 `NO_PROXY` 和 `no_proxy` 设成同一份：合并两个名字原有的排除项（agent 的额外变量和 daemon 环境里的都算），再加上 `127.0.0.1`，免得它继承的代理把转发请求和令牌带到别处（有的客户端两个都设时只认其中一个，所以两个必须一致；合并后给单个 agent 设的 `NO_PROXY` 也会带上 daemon 环境里的排除项，没法再用它让某个主机强制走代理）；转发到真实地址时用 daemon 自己的代理设置（`HTTPS_PROXY` / `NO_PROXY` 等，回环地址不走代理），给单个 agent 配的额外代理变量对经转发的模型请求不起作用。令牌只在本机 127.0.0.1 上有用、daemon 重启即作废，所以不当作密钥脱敏。Claude Code、Codex 和 OpenCode 的其他模式仍直接连。
- 注入的 key 和额外变量（8 个字符以上）加入脱敏名单，不会出现在会话事件、最终回复和数据库里。`PATH`、`HOME` 等系统变量和 `HMESH_` 开头的变量不能被覆盖。改了模型服务后，新会话和已有会话的下一轮会用新的进程。
- **测试连接**（`/local/agents/{id}/service/test`，同样只有本机 owner 能调，没有 peer 接口）会把 key 发给填写的地址：只在 owner 点按钮或运行 `hmesh agent service … --test` 时发生。先请求模型列表（OpenAI 协议使用 `GET {地址}/models`，Anthropic Messages 使用 `GET {根地址}/v1/models`），不花 token；列不出来才用默认模型发一次最小的请求（Chat 接口 `max_tokens=1`；Anthropic Messages 走 `/v1/messages`；OpenAI Responses 走 `POST {地址}/responses`，`max_output_tokens=16`）；key 被拒（401/403）或连不上就直接报告，不再发第二次。不跟随重定向（避免把 key 带到别的地址），回环地址不走代理，整次测试 13 秒内结束。返回值、报错和审计记录（`agent.service.test`，只记模式和成败）里都不含 key，服务商回包里如果引用了 key 也会被替换。
- **检测 agent 自己的配置**（`/local/agents/{id}/service/check`，只有本机 owner 能调）只问 agent 自己：先用 ACP 的 `auth/status`（claude-agent-acp 会回答，也接收它推送的 `_auth/status_update`），再跑它自带的只读状态命令（Codex `codex login status`、OpenCode `opencode auth list`、Pi `pi --list-models`）。**不读任何 agent 的凭据文件，也不运行会打印凭据的命令**（如 `pi auth`）；不建会话、不调模型；每个命令最多等 10 秒。检测结果（登录方式、账号邮箱）存在 `<数据目录>/agent-login/<agent id>.json`（0600），只在本机弹窗显示；配对电脑只从 agent 卡片的 `own_login` 看到「已配好 / 没配好 / 看不出来」。`codex login status` 给 API key 时会带 key 的前后几位，HarnessMesh 只保留「API key」这个结论。审计记录 `agent.service.check` 只记三态结果。
- **key 只填环境变量名**：owner 可以让 key 在启动 agent 时从 daemon 的某个环境变量读取（`api_key_env`），设置文件里只存变量名。变量没设就不启动 agent，并在会话里说明缺哪个变量。读到的值和存下的 key 一样加入脱敏名单。系统变量和 `HMESH_` 开头的变量不能用。
- **Claude Code 接第三方地址**时，选了默认模型就同时设 `ANTHROPIC_MODEL`、`ANTHROPIC_DEFAULT_OPUS/SONNET/HAIKU_MODEL` 和 `CLAUDE_CODE_SUBAGENT_MODEL`（否则它会发出 Claude 自己的模型名），并设 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`，避免它拿别家的 key 去请求 Anthropic 的后台服务。

## MCP 服务器的权限

`hmesh mcp`（`hmesh-mcp`）是本机程序，使用本机 owner 的 RPC 客户端身份。模型只看到六个固定会话工具，拿不到私有 token、任意路径读取、配对或 policy 修改、批准接口。能读到节点目录的本机进程本来就能拿到 owner 身份，MCP 服务器没有扩大这个范围。

HarnessMesh 注入给会话的服务器带 `--session <id>` 启动：会话不存在或已关闭时拒绝启动，不会退化成不受限的 owner 模式；它只能操作自己这个会话打开的子会话，打开的子会话带上调用链。调用链最多 3 层、不能回到链上已有的 agent、同一会话最多 4 个运行中的子会话；**别的电脑打开的会话（以及它的后代）只能叫本机的 agent**，不能借本机身份连到第三台电脑。执行端仍按自己对来源电脑的访问模式决定是否需要确认；远端返回的文本按不可信数据处理。详见 `docs/mcp.md`。

**这些限制只管 MCP 工具，不是进程隔离。** agent 进程以当前用户身份运行，能读到节点目录（包括 owner 证书和 token）。一旦你批准它执行 shell 命令（`execute` 类权限），它就可以直接运行 `hmesh session open --peer …` 等命令，以本机 owner 身份做任何 owner 能做的事，包括连到其他配对电脑。所以：对别的电脑或别的 agent 打开的会话，批准 shell 权限前要想清楚；只想让 agent 互相对话时，拒绝 shell 权限即可。

已知凭据值在 text delta（包括跨 delta 的值）、工具事件文本和 stderr 中脱敏。原生工具参数和输出不作为公共事件转发。不要主动把密钥放入任务正文、工件或输出；任务正文和运行历史是需要私有保存的数据。未承诺对任意编码/变换后的秘密进行识别。

## 取消、崩溃和恢复

Windows 在发送 prompt 前将进程放入 kill-on-close Job Object，终止时确认 Job 中活跃进程为零；只追踪当前 attempt 的进程。Unix 使用专用进程组，无法保证已脱离进程组的子进程被包含。无法证明退出时返回 UNKNOWN。它们均不是通用进程沙箱。

受控 Rust 测试进程已覆盖运行中取消、超时、子进程清理、异常输出和 Windows Daemon 硬退出恢复。会话的取消走 ACP `session/cancel`，挂起的权限请求按协议回答 `cancelled`；daemon 重启后进行中的轮次标为中断，不自动重发。真实 agent 的 ACP 取消与 `session/load` 还没有逐一真机验证。Managed Run 采用进程树终止；Probe 中未测试的取消/恢复项保持明确标记。

SQLite 去重避免同一请求创建第二次尝试，不承诺跨外部副作用的 exactly-once。Daemon 崩溃后的运行结果归 UNKNOWN，需要用户检查副作用；不得自动重试。

## 验证范围

本机测试覆盖错误 pin、匿名/未配对访问、owner 凭据分离、发送方伪造、未知项目/远端 cwd、跨 origin 读取、未批准拒绝、去重、签名重放、策略热更新和信任撤销。测试进程和协议 fixture 与真实模型证据分开。

`cargo run --locked -p xtask -- audit` 通过官方 OSV querybatch 查询整个锁文件（包含其他目标平台），处理分页且遇到不完整结果直接失败。报告含时间和锁文件 hash。安全数据库随时间变化，需要在发布前重新执行；最近一次报告位于 `docs/evidence/dependency-audit.json`。

真实验收已覆盖 V0 本机 Windows、SSH 双向 Pi/DSH、断线与发起端重启后的补读/去重，以及 Pi 1.4.0 原生 MCP 委派 DSH 的独立审批和父子产物核验。Unix 硬崩溃时对 detached 子进程的清理仍不在已验证能力内。Windows 和 Orion/Linux 本地回归已执行；CI 已配置三平台，尚无远端 CI 执行证据。完整 V0.1 的 Tailscale、Codex/Mac↔Windows 链路仍需验收。见 `docs/ssh-bidirectional-mcp.md`。
